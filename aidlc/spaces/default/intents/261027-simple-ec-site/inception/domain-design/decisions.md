## ADR-001: 業務 4 コンポーネント＋アダプター（六角形アーキテクチャ）で構成する

### Context

- 業務の関心ごとは「コース」「利用資格」「予算」「購入」で、それぞれ変更の理由と頻度が異なる（`domain-design-questions.md` Q1 で 4 分割を選択）。
- データ保存は本来 PostgreSQL だが、今回はメモリ上のモックに差し替えて動かす（要件 C8、NFR7）。
- 関数型で、オブジェクト指向の設計を避けるという制約がある（要件 C6、NFR6）。

### Decision

業務ロジックを CourseCatalog・Eligibility・TrainingBudget・Purchasing の 4 コンポーネントに分ける。外界との接続（HTTP、データ保存、画面）は WebApi・InMemoryStore・WebUi のアダプターに置き、業務コンポーネントはアダプターに依存しない。業務コンポーネントは、必要なデータの読み書きを「関数の形（型）」として定め、アダプターがその形の関数を実装する。インターフェースを持つオブジェクトではなく、関数を受け渡すことで依存を逆転させる。

### Consequences

- 良い点: 業務ロジックをデータストアや HTTP なしに単体テストできる（NFR8）。メモリ実装を PostgreSQL の実装に差し替えても業務ロジックは変わらない（NFR7）。
- 悪い点: コンポーネントの数が増え、起動時の組み立て（WebApi）が長くなる。関数の形の定義が増える。
- セキュリティ: 購入の可否と金額の判断を業務コンポーネント（サーバー側）に閉じ込めることで、画面からの改ざんに影響されない（NFR3）。

### Alternatives Rejected

- **3 分割（アカウントに企業・従業員・予算をまとめる）**: 利用資格と予算の変更理由が異なり、片方の変更がもう片方に波及する。
- **2 分割（購入に利用資格・予算・チケットをまとめる）**: 購入が肥大化し、予算計算や利用資格判定を単独で検証しにくい。
- **層構造（画面・業務・データの 3 層）でデータ層に直接依存する**: 業務ロジックが保存方法に依存し、PostgreSQL への差し替えで業務ロジックの変更が必要になる。

## ADR-002: 研修予算を追記のみの取引として記録し、残高は計算する

### Context

- 購入は「チケットの発行」と「予算の消費」を同時に行い、片方だけが反映された状態を残してはならない（FR5.3、NFR2）。
- 不変データと副作用の最小化を重視する（C6、NFR6）。
- `domain-design-questions.md` Q2 で「取引を追記し残高は計算」を選択。

### Decision

予算は BudgetEntry（付与・消費）の追記だけで記録し、変更・削除をしない。残高は従業員ごとに「付与の合計 − 消費の合計」で計算する。消費の取引はチケット ID を持ち、どの購入で使われたかを追える。

### Consequences

- 良い点: 書き換えがないため、関数型の不変データと相性がよい。購入の記録は「チケットと消費取引を追加する」だけになり、整合性を保ちやすい。経緯を追える。
- 悪い点: 残高を求めるたびに取引を合計する。今回の規模（従業員数名・取引数十件）では問題にならないが、将来の大規模化では集計の工夫（スナップショットなど）が必要になる。
- セキュリティ: 改ざんされにくい記録の形であり、将来の監査に使える。

### Alternatives Rejected

- **現在の残高だけを持ち、購入時に書き換える**: 実装は単純だが、書き換えと発行の同時性を別途保証する必要があり、経緯も失われる。

## ADR-003: 残席数は保存せず「定員 − 発行済みチケット数」で計算する

### Context

- 定員を超えて発行してはならない（FR5.8、NFR2）。残席数が負になってはならない。
- `domain-design-questions.md` Q3 で「定員とチケット数から計算」を選択。

### Decision

開催日程（Session）には定員（capacity）だけを持つ。残席数は「定員 − その日程の発行済みチケット数」で計算する。チケットを唯一の記録とする。

### Consequences

- 良い点: 残席数とチケットの数が食い違うことがない。購入の記録はチケットの追加だけで、残席数の書き換えが不要。
- 悪い点: 一覧の表示や「空席ありのみ」の絞り込みのたびに、日程ごとの発行済み数を数える必要がある。今回の規模では問題にならない。
- セキュリティ: 特になし。

### Alternatives Rejected

- **開催日程に残席数を持ち、購入時に 1 減らす**: 読み出しは速いが、チケットと残席数の 2 か所を同時に正しく更新し続ける必要がある。

## ADR-004: 購入を「純粋な決定関数」と「データストアでの一括記録」に分ける

### Context

- 購入では、利用資格・日程の存在・受付終了・満席・購入済み・残高不足をすべて検証し、1 つでも満たさなければ何も変えない（FR5.2）。
- 最後の 1 席に同時に購入が届いても 1 件だけ成功させる（FR5.8）。
- 副作用を境界に閉じ込める（NFR6）。

### Decision

購入を 2 段に分ける。

1. **決定（純粋関数、Purchasing）**: 「現在のデータの写し」を受け取り、「チケット 1 枚＋消費取引 1 件」か「拒否の理由」を返す。副作用を持たない。
2. **記録（InMemoryStore）**: 状態の更新を 1 か所で直列に行い、記録の直前に最新の状態から写しを作って決定関数をもう一度評価する。決定が成功ならチケットと消費取引を同時に反映し、拒否なら何も反映しない。

### Consequences

- 良い点: 購入のルールを、時刻や保存方法に依存せずに単体テストできる。直列化された 1 回の更新の中で検証と記録を行うため、同時購入でも定員を超えない。
- 悪い点: 更新が直列化されるため、書き込みの並行性は低い（今回の規模では問題にならない）。PostgreSQL へ移すときは、同じ保証をトランザクションと行ロック（または一意制約）で実現する必要がある。
- セキュリティ: 金額はコースのデータから決め、要求の値を使わない（FR5.5）。重複購入はデータストア側でも防ぐ。

### Alternatives Rejected

- **各コンポーネントが順に自分のデータを更新し、失敗したら取り消す（補償処理）**: 途中失敗時に不整合な中間状態が生まれ、取り消しの処理も必要になる。
- **画面側の確認だけで重複・満席を防ぐ**: 二重送信や同時購入、API の直接呼び出しを防げない。

## ADR-005: コースカタログは発行済み数を関数として受け取り、購入への依存を持たない

### Context

- 探索（空席ありのみ、空席のある日程の数）と日程の状態判定には、日程ごとの発行済みチケット数が必要（ADR-003）。
- 一方、Purchasing は日程・受講料の参照のために CourseCatalog に依存する。CourseCatalog が Purchasing に依存すると循環になる。

### Decision

CourseCatalog の探索・状態判定の関数は、「日程 ID → 発行済み数」を返す関数を引数として受け取る（高階関数）。この関数は起動時に WebApi が、データストアのチケット集計を部分適用して渡す。

### Consequences

- 良い点: 依存の循環がなく、CourseCatalog をチケットなしで単体テストできる（テストでは任意の関数を渡せる）。
- 悪い点: 関数の引数が増える。発行済み数の数え方は呼び出し側に分散する。
- セキュリティ: 特になし。

### Alternatives Rejected

- **CourseCatalog が Purchasing を直接呼ぶ**: 循環依存になる。
- **探索専用の読み取りコンポーネントを別に作る**: 責務は分かれるが、今回の規模ではコンポーネントが増えるだけで効果が小さい。

## ADR-006: 探索は Web API で行い、画面は非同期の部分更新で表示する

### Context

- 探しやすさが UX の重点で、条件の変更から 300 ms 以内に表示へ反映したい（NFR1、US1.2）。
- `domain-design-questions.md` Q4 で「Web API で行い、全画面の読み込みはせず Ajax 的に解決」を選択。
- 将来は PostgreSQL の検索に置き換えたい（C8）。

### Decision

絞り込みと並べ替えは WebApi 経由で CourseCatalog が行う。WebUi は条件が変わるたびに API を非同期で呼び、結果部分だけを差し替える（ページ全体の再読み込みはしない）。連続した入力では、最後の要求の結果だけを反映する。探索条件は URL のクエリに反映し、URL から復元する。

### Consequences

- 良い点: 探索ロジックが 1 か所にまとまり、画面とずれない。DB の検索に置き換えやすい。全画面の読み込みがないため体感が速い。
- 悪い点: 入力のたびに通信が発生する（ローカルでは問題にならない）。古い応答の取り扱い（最後の要求だけを反映）が必要になる。
- セキュリティ: API は探索条件の値を検証し、不正な値は 4xx または無視する（NFR3、US1.8）。

### Alternatives Rejected

- **画面で全件を受け取り、ブラウザ内で絞り込む**: 反応は速いが、ロジックが画面側に寄り、DB 検索への置き換えでロジックの移し替えが必要になる。
- **画面と API の両方で行う**: 同じロジックが 2 言語（MoonBit と Rust）に重複し、食い違いの原因になる。

## ADR-007: 画面を The Elm Architecture（TEA）で組み立てる

### Context

- 画面の言語は MoonBit で、関数型を全面的に使い、オブジェクト指向を避ける（C3、C6）。
- 非同期の部分更新（ADR-006）、URL との同期、読み込み中・0 件・失敗の状態の出し分けが必要。
- `domain-design-questions.md` Q5 で TEA を選択。

### Decision

画面全体の状態を 1 つの不変なデータで持つ。「メッセージ＋状態 → 新しい状態＋コマンド」を返す更新関数と、「状態 → 画面」を返す描画関数はどちらも純粋関数とする。API 呼び出し・URL の書き換え・時刻の取得はコマンドとして実行環境に任せる。MoonBit で TEA を実現する具体的なライブラリ（または自作の薄い実行環境）は、アプリケーション側の技術選定で決める（要件 OQ1）。

### Consequences

- 良い点: 状態遷移を純粋関数としてテストできる。状態が 1 か所にあるため、読み込み中・失敗などの状態の組み合わせを漏れなく扱いやすい。
- 悪い点: メッセージの種類が増えると更新関数が長くなる。MoonBit 向け TEA の成熟度によっては、実行環境の一部を自作する必要がある。
- セキュリティ: 画面は購入可否の最終判断をしない（表示上の無効化のみ）。最終判断は API が行う（NFR3）。

### Alternatives Rejected

- **画面ごとに独立した状態と処理を持つ**: 画面間で共有する情報（操作中の従業員、残高）の受け渡しが増え、状態の食い違いが起きやすい。

## ADR-008: 操作中の従業員を要求の従業員 ID で識別し、認証済みとして扱う

### Context

- ログイン機能は作らない。利用者は社内ポータルで認証済みとみなす（FR1.1、要件 `[Q2-1]`）。
- ローカル検証のため、画面で従業員を切り替えられる必要がある（FR1.2）。
- 契約外の企業の従業員による購入は、API が拒否しなければならない（FR1.3）。

### Decision

WebUi は、切り替えで選んだ従業員 ID を API の各要求に付けて送る（具体的な受け渡し方法（HTTP ヘッダーなど）は後の工程で決める）。WebApi はその ID を認証済みの従業員として扱い、購入では Eligibility が利用資格を判定する。

### Consequences

- 良い点: ログインなしで、検証用の切り替えと利用資格の判定を両立できる。将来は、社内ポータルの認証情報から従業員 ID を取り出す処理に差し替えるだけで済む。
- 悪い点: 従業員 ID を偽れば他人として操作できる。ローカル検証専用の前提であり、そのまま公開環境に置いてはならない。
- セキュリティ: 上記のなりすましの危険を認識した上で、ローカル検証に限定する（要件 C1、対象外: 認証機能）。README とコードのコメントに、公開環境では使えないことを明記する。

### Alternatives Rejected

- **ログイン画面とセッションを作る**: 要件の対象外（認証機能を作らない）で、シンプルさを損なう。
- **サーバー起動時の設定で従業員を 1 人に固定する**: 画面での切り替え（FR1.2）ができない。
