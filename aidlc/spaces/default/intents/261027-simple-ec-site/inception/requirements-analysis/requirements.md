# 要件定義書 — 研修コース e チケット購入サイト

## 1. 意図分析（Intent Analysis）

| 観点 | 内容 |
| --- | --- |
| ご依頼 | 優れたユーザー体験を備えたシンプルな EC サイトを構築する。ローカルでの動作検証までとし、クラウドへのデプロイは行わない `[desc]` |
| 具体化した姿 | 契約企業の従業員が、研修予算（ポイント）を使って研修コースの受講用 e チケットを購入するサイト（社内向け LMS の購入窓口に近いもの） `[Q1]` `[Q2]` `[Q3]` |
| 目的（ゴール） | 従業員が受けたい研修コースをすぐに見つけ、空席のある日程を選んで、迷わず購入を終えられること `[Q5]` `[Q8]` |
| 種別 | 新規開発（Greenfield） |
| 範囲 | 従業員向けの購入画面（MoonBit）と Web API（Rust）を 1 つの monorepo で構成する `[Q7-1]` `[確認時のご指摘]` |
| 複雑度 | 標準（認証・決済・管理画面を対象外にして単純化。予算と定員の整合性がおもな難所） |
| 深さ | Standard |

### 主要な利用の流れ

1. 従業員（認証済みとみなす）がコース一覧を開く
2. キーワード・カテゴリ・空席の有無などでコースを探す
3. コースの詳細で、空席のある開催日程を選ぶ
4. 購入確認で研修予算の残高と購入後の残高を確かめ、購入を確定する
5. 発行された e チケットを確認する

## 2. 機能要件（Functional Requirements）

### FR1. 利用者アカウントの扱い `[Q2]` `[Q2-1]`

- **FR1.1** システムは、利用者をすでに認証済みの従業員として扱い、ログイン画面を提供しない。
- **FR1.2** システムは、ローカル検証用に、画面上で操作中の従業員アカウントを切り替える手段を提供する。切り替えると、予算残高・購入済みチケットなどの表示がそのアカウントのものに変わる。
- **FR1.3** システムは、契約中の企業に所属する従業員のアカウントからの購入だけを受け付ける。契約中でない企業の従業員、または存在しない従業員 ID による購入要求は、Web API が拒否する（画面の表示に頼らない）。
- **FR1.4** 初期データには、動作確認のため、契約中の企業の従業員を複数名と、契約が終了した企業の従業員を 1 名以上含める。

受け入れ基準:

- Given 契約中の企業の従業員 A を選択している, When 画面上で従業員 B に切り替える, Then ヘッダーの表示名と予算残高が B のものに変わる
- Given 契約が終了した企業の従業員を選択している, When 空席のある日程を購入しようとする, Then 購入は拒否され「ご所属の企業は現在このサービスをご利用いただけません」という趣旨のメッセージが表示され、予算と空席数は変化しない

### FR2. コースの一覧と探索 `[Q1]` `[Q8]`

- **FR2.1** システムは、コースを一覧で表示する。各コースに、コース名・カテゴリ・概要・受講料（ポイント）・直近の開催日・空席のある日程の数を表示する。
- **FR2.2** システムは、キーワードでコースを絞り込める。対象はコース名と概要で、空白区切りの複数語はすべてを含むもの（AND）に絞り込む。全角と半角、英字の大文字と小文字は区別しない。
- **FR2.3** システムは、カテゴリ（例: マネジメント、技術、ビジネススキル、コンプライアンス）でコースを絞り込める。
- **FR2.4** システムは、「空席のある日程があるコースのみ」に絞り込める。
- **FR2.5** システムは、開催期間（開始日〜終了日）でコースを絞り込める。指定した期間内に空席のある日程を 1 つ以上持つコースだけを表示する。
- **FR2.6** システムは、コースを「開催日が近い順」「受講料の安い順」「受講料の高い順」「コース名順」で並べ替えられる。同じ値のコースはコース ID の昇順で並べ、表示順を毎回同じにする。
- **FR2.7** システムは、現在の条件に合うコースの件数を表示する。
- **FR2.8** システムは、絞り込み・並べ替えの条件を URL に反映する。その URL を再読み込みしたり共有したりしても、同じ条件の結果が表示される。
- **FR2.9** 条件に合うコースが 0 件のとき、システムは「条件に合うコースがない」ことと、条件をリセットする操作を表示する。読み込み中・0 件・読み込み失敗は、それぞれ別の表示にする。

受け入れ基準:

- Given コース一覧を表示している, When キーワード欄に「リーダー　研修」（全角スペース区切り）と入力する, Then コース名または概要に「リーダー」と「研修」の両方を含むコースだけが表示され、件数表示も更新される
- Given カテゴリ「技術」と「空席ありのみ」を選択している, When 「受講料の安い順」に並べ替える, Then 技術カテゴリで空席のある日程を持つコースだけが受講料の昇順で表示される
- Given 絞り込み条件を指定した URL を開く, When ページを再読み込みする, Then 同じ条件と同じ結果が表示される
- Given どのコースにも一致しないキーワードを入力した, When 一覧が更新される, Then 0 件であることと「条件をリセット」操作が表示され、操作するとすべてのコースが表示される
- Given Web API が応答しない, When コース一覧を開く, Then 読み込みに失敗したことと再試行の操作が表示される

### FR3. コースの詳細と日程の選択 `[Q5]`

- **FR3.1** システムは、コースの詳細（コース名・カテゴリ・概要・受講料・所要時間・形式（オンライン／会場）・開催日程の一覧）を表示する。
- **FR3.2** システムは、開催日程ごとに開催日時・会場または形式・定員・残席数を表示する。
- **FR3.3** システムは、残席のある日程だけを選択できるようにする。満席の日程と、開催日時がすでに過ぎた日程は、選択できない状態で理由（「満席」「受付終了」）と共に表示する。
- **FR3.4** 操作中の従業員がすでに購入済みの日程は「購入済み」と表示し、選択できないようにする。
- **FR3.5** 存在しないコース ID を開いた場合、システムは「コースが見つからない」ことと一覧へ戻る操作を表示する。

受け入れ基準:

- Given 定員 10 名で残席 0 の日程がある, When コース詳細を表示する, Then その日程は「満席」と表示され選択できない
- Given 開催日時を過ぎた日程がある, When コース詳細を表示する, Then その日程は「受付終了」と表示され選択できない
- Given 残席 3 の日程がある, When その日程を選択する, Then 購入確認へ進む操作が有効になる

### FR4. 研修予算（ポイント） `[Q3]`

- **FR4.1** システムは、従業員ごとに研修予算の残高（ポイント、整数）を持ち、画面上に常に表示する。
- **FR4.2** 受講料はポイント（整数）で表す。1 枚の購入で受講料と同額のポイントを残高から差し引く。
- **FR4.3** 残高が受講料に満たない場合、システムは購入を受け付けない。画面では購入確認の時点で不足額を表示し、確定操作を無効にする。Web API も同じ条件で購入を拒否する。
- **FR4.4** 残高がちょうど受講料と同額の場合は購入でき、購入後の残高は 0 になる。

受け入れ基準:

- Given 残高 30,000 pt の従業員が受講料 25,000 pt の日程を選んだ, When 購入確認を開く, Then 現在の残高 30,000 pt、受講料 25,000 pt、購入後の残高 5,000 pt が表示される
- Given 残高 20,000 pt の従業員が受講料 25,000 pt の日程を選んだ, When 購入確認を開く, Then 不足額 5,000 pt が表示され、確定操作は無効になっている
- Given 残高 25,000 pt の従業員が受講料 25,000 pt の日程を購入した, Then 購入は成功し残高は 0 pt になる

### FR5. 購入（e チケットの発行） `[Q1]` `[Q3]` `[Q5]`

- **FR5.1** システムは、購入を確定する前に確認画面を表示する。確認画面には、コース名・開催日時・会場または形式・受講料・現在の残高・購入後の残高を表示する。
- **FR5.2** 購入の確定時、Web API は次をすべて検証し、1 つでも満たさなければ購入を拒否して、予算と残席を一切変更しない。
  - 従業員が契約中の企業に所属している（FR1.3）
  - 日程が存在し、開催日時を過ぎていない
  - 日程に残席が 1 以上ある
  - その従業員がその日程をまだ購入していない
  - 予算の残高が受講料以上である
- **FR5.3** すべての検証を通過した場合、Web API は残席を 1 減らし、予算から受講料を差し引き、e チケットを発行する。この 3 つは 1 つの処理単位として扱い、一部だけが反映された状態を残さない。
- **FR5.4** 1 回の購入で発行する e チケットは、1 名・1 日程につき 1 枚とする。
- **FR5.5** 受講料の金額は、Web API がコースのデータから決める。画面から送られた金額は使わない。
- **FR5.6** 確定操作の実行中は確定ボタンを無効にし、連打しても購入が 2 回処理されないようにする。Web API 側でも、同じ従業員による同じ日程の重複購入を拒否する（FR5.2）。
- **FR5.7** 購入を拒否した場合、システムは理由（満席になった、受付終了、残高不足、購入済み、利用できない企業）が分かるメッセージを表示し、利用者が次に取れる操作（別の日程を選ぶ、一覧へ戻る）を示す。
- **FR5.8** 最後の 1 席に同時に 2 件の購入要求が届いた場合、1 件だけが成功し、もう 1 件は「満席」として拒否される。

受け入れ基準:

- Given 残席 1・受講料 10,000 pt の日程と、残高 50,000 pt の従業員, When 購入を確定する, Then e チケットが発行され、残席は 0、残高は 40,000 pt になる
- Given 購入確認を表示している間に、別の従業員がその日程の最後の 1 席を購入した, When 確定する, Then 「満席になった」趣旨のメッセージが表示され、残高は変わらない
- Given 確定ボタンを素早く 2 回押した, When 処理が終わる, Then 発行された e チケットは 1 枚で、残高の減少も 1 回分だけである
- Given 同じ日程を購入済みの従業員, When Web API に同じ日程の購入要求を直接送る, Then 要求は拒否され、残高と残席は変わらない
- Given 画面から受講料を 1 pt に改ざんした購入要求, When Web API に送る, Then 受講料はコースのデータの金額で差し引かれる

### FR6. e チケットの表示 `[Q1]`

- **FR6.1** 購入が成功すると、システムは e チケットを表示する。e チケットには、チケット番号・従業員名・コース名・開催日時・会場または形式・購入日時・支払ったポイントを含める。
- **FR6.2** チケット番号は、ほかのチケットと重複しない番号とする。
- **FR6.3** システムは、操作中の従業員の購入済み e チケットを一覧表示する。並びは開催日時の近い順とする。購入済みのチケットがない場合は、コースを探す操作を案内する。

受け入れ基準:

- Given 購入が成功した, When 完了画面が表示される, Then チケット番号・コース名・開催日時・支払ったポイントが表示される
- Given 2 枚購入済みの従業員, When 購入済みチケットの一覧を開く, Then 2 枚が開催日時の近い順に表示される
- Given 購入済みのチケットがない従業員, When 一覧を開く, Then チケットがないことと、コース一覧へ移動する操作が表示される

### FR7. 初期データ `[Q4]`

- **FR7.1** コース・開催日程・企業・従業員・予算は、起動時に初期データとして読み込む。運営者向けの管理画面は作らない。
- **FR7.2** 初期データには、探索機能を確認できるだけの種類（4 カテゴリ以上、12 コース以上、満席の日程・受付終了の日程・残席わずかの日程を含む）を用意する。
- **FR7.3** 開催日程は、起動した日を基準に未来の日時として生成し、いつ起動しても購入できる日程が存在するようにする。受付終了の確認用に、過去の日程も含める。

## 3. 非機能要件（Non-Functional Requirements）

| ID | 区分 | 要件 | 確認方法 |
| --- | --- | --- | --- |
| **NFR1** | 性能 | ローカル環境で、コース一覧・詳細の Web API は 200 ms 以内に応答する（初期データの規模で、95% の要求）。画面の絞り込み・並べ替えは、条件を変えてから 300 ms 以内に表示へ反映する | Web API のテストで応答時間を測る／目視 |
| **NFR2** | 信頼性・整合性 | 予算の残高と残席数は負の値にならない。購入処理は全部反映か、まったく反映しないかのどちらかとする（FR5.3）。同時購入でも定員を超えて発行しない（FR5.8） | 同時実行を含む Web API のテスト |
| **NFR3** | セキュリティ | Web API は、すべての入力（ID の形式、存在、権限）を検証し、不正な要求には 4xx で応答する。購入の可否・金額の判断を画面に任せない。秘密情報をコードに埋め込まない | Web API のテスト／コードレビュー |
| **NFR4** | ユーザビリティ | 「コース一覧 → 日程選択 → 購入確認 → 完了」の主要な流れを、ページ遷移 3 回以内で完了できる。読み込み中・0 件・失敗の表示を区別する（FR2.9） | E2E 確認 |
| **NFR5** | アクセシビリティ（基本） | 主要な流れをキーボードだけで操作できる。フォーム部品とボタンに名前（ラベル）がある。状態（満席・購入済みなど）を色だけで伝えない | 手動確認 |
| **NFR6** | 保守性（実装スタイル） | 関数型パラダイムで実装する。データは不変（イミュータブル）として扱い、副作用は入出力の境界（HTTP、データストア、画面描画）に閉じ込める。処理の組み立てには高階関数とクロージャを使い、クラス階層や可変な内部状態を持つオブジェクトによる設計を避ける | コードレビュー |
| **NFR7** | 保守性（データアクセス） | データの読み書きはリポジトリの境界を通して行う。今回はメモリ上のデータストアで実装し、ドメインの処理を変えずに PostgreSQL などの実装へ差し替えられる形にする | コードレビュー／テストで差し替え可能なことを確認 |
| **NFR8** | テスト容易性 | ドメインの処理（探索、購入の検証、予算計算）は純粋関数として単体テストできる。Rust は `cargo test`、MoonBit は `moon test` で、手作業の準備なしに実行できる | テストの実行 |
| **NFR9** | 実行容易性 | 前提ツール（Rust、MoonBit）を入れた環境で、README の手順に従い、リポジトリのルートからのコマンドでビルドと起動ができる | README の手順どおりに起動 |
| **NFR10** | 可観測性（最小） | Web API は、要求ごとにメソッド・パス・状態コード・処理時間をログに出す。購入の拒否は理由をログに残す。ログに個人の連絡先などは出さない | ログの目視 |

## 4. 制約（Constraints）

| ID | 制約 | 出典 |
| --- | --- | --- |
| C1 | クラウドへのデプロイは行わない。ローカルでの動作検証までとする | `[desc]` |
| C2 | ドキュメントとチャットの応答は日本語で書く | `[desc]` |
| C3 | 画面は MoonBit の最新版で実装し、JavaScript 向けにビルドしてブラウザで動かす | `[Q7]` `[Q7-1]` |
| C4 | Web API は Rust の最新 stable 版で実装する | `[Q7]` `[Q7-1]` |
| C5 | ライブラリ（crate、MoonBit パッケージ）は、デファクトスタンダードなものの最新 stable 版を積極的に使う | `[Q7]` |
| C6 | 関数型パラダイムを全面的に採用し、オブジェクト指向の設計を避ける（NFR6） | `[Q7]` |
| C7 | 画面と Web API を 1 つのリポジトリで管理する monorepo 構成にする | `[確認時のご指摘]` |
| C8 | 本来のデータ保存先は PostgreSQL などの DB サーバーとし、今回はリポジトリの実装をメモリ上のデータストアに差し替えたモックで動かす | `[Q6]` |

## 5. 前提（Assumptions）

| ID | 前提 | 理由 |
| --- | --- | --- |
| A1 | カートは設けず、1 回の購入で 1 つの日程を購入する | ご回答の流れ（コース選択 → 空席の日程を選択 → 購入）に沿うため `[Q5]` |
| A2 | 1 名の従業員が同じ日程を購入できるのは 1 枚まで。同じコースの別日程は購入できる | e チケットは本人の受講用であり、同じ日程を 2 枚持つ用途がないため |
| A3 | 1 ポイントの価値や円との換算は扱わない。受講料と予算はどちらもポイントの整数で表す | 実際の決済を行わないため `[Q3]` |
| A4 | 予算の付与・追加、購入の取り消し・返金は扱わない（初期データの残高を使う） | 管理機能を作らないため `[Q4]` |
| A5 | データはメモリ上にあり、Web API を再起動すると初期データに戻る | `[Q6]` |
| A6 | 日時は日本時間（Asia/Tokyo）で表示し、「開催日時を過ぎたか」の判定は Web API の時計で行う | 利用者が日本の企業の従業員であるため |
| A7 | e チケットのメール送信や PDF 出力は行わず、画面上の表示のみとする | ローカル検証のみで、外部サービスと連携しないため `[desc]` |
| A8 | UX の重点は探しやすさ（FR2）に置く。そのほかの UX（日程選択と購入の快適さ、購入の安心感、アクセシビリティ、レスポンシブ）は、FR3〜FR6 と NFR4・NFR5 の基本水準にとどめる | `[Q8]` で選択されたのは探しやすさのみのため |
| A9 | 対応ブラウザは最新版の Chrome・Edge・Firefox・Safari とする | ローカル検証用のため |

## 6. 対象外（Out of Scope）

- ログイン・ログアウト・会員登録などの認証機能 `[Q2]`
- 実際の決済、個人払い、会社への請求処理 `[Q3]`
- 研修担当者・運営者向けの管理画面（コースの登録・編集、購入状況の確認） `[Q4]`
- 購入の取り消し・返金・予算の追加付与
- PostgreSQL などの実データベースとの接続（リポジトリの境界のみ用意する） `[Q6]`
