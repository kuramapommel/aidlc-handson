## 複数のユニットにまたがるもの

**受け入れ基準が複数のユニットにまたがるストーリーはない。** どのユニットも、担当するストーリーの受け入れ基準をすべて自分の中で満たし、後続のユニットがなくても完了と判定できる。

当初案では 3 つの受け入れ基準（AC2.1.3、AC3.5.3、AC4.1.3）が後続のユニットの機能に依存していた。疎結合を保つため、ユーザーストーリー側で次のように組み直した（`../user-stories/stories.md` の「変更履歴」）。

| 受け入れ基準 | 組み直し | 担当ユニット |
| --- | --- | --- |
| 詳細から一覧へ戻ったときの条件の保持（旧 AC2.1.3） | US1.8 の AC1.8.4 へ移動 | U2 |
| 購入できたかの確認方法の案内（AC3.5.3） | 案内先を、U1 にあるコースの詳細の「購入済み」表示に変更 | U1 |
| 完了画面から購入済みチケットへの移動（旧 AC4.1.3 の一部） | US4.2 の AC4.2.4 へ移動。ヘッダーからの移動（AC4.2.5）も U3 に追加 | U3 |

受け入れ基準ではなく、コードを共有する部分は次のとおり。後続のユニットは、U1 が用意した共有部分に「追加」するだけで、U1 の振る舞いは変えない。

| 共有するコード | 用意するユニット | 追加するユニット | 内容 |
| --- | --- | --- | --- |
| ヘッダー（従業員名・残高・切り替え） | U1 | U3 | U3 はヘッダーに「購入済みチケット」への導線を追加する（AC4.2.5） |
| 完了画面 | U1 | U3 | U3 は完了画面に「購入済みチケットを見る」を追加する（AC4.2.4） |
| コース一覧の画面と受け口 | U1 | U2 | U2 は探索条件の入力・結果更新・URL 同期を追加する |

## ユニット内の実装順

| ユニット | 実装順 |
| --- | --- |
| U1 | monorepo の土台と 2 プロセスの起動 → 業務ロジック（CourseCatalog・Eligibility・TrainingBudget・Purchasing の型と純粋関数）→ InMemoryStore と初期データ → WebApi の受け口 → WebUi（ヘッダー → 一覧（US1.1）→ 詳細と日程（US2.1〜US2.3）→ 購入確認（US3.1・US3.2）→ 購入と完了（US3.3〜US3.5・US4.1）→ 契約外の案内（US5.1）） |
| U2 | 探索条件の型と検証 → 絞り込み（US1.2〜US1.5）→ 並べ替え（US1.6、続けて US1.7）→ Web API の条件の受け付け → 画面の非同期更新と URL 同期（US1.8）→ 0 件・失敗の表示（US1.9） |
| U3 | 従業員ごとのチケット一覧の関数 → Web API の受け口 → 一覧画面と詳細表示（AC4.2.1〜AC4.2.3）→ 完了画面とヘッダーへの導線の追加（AC4.2.4・AC4.2.5） |

## 割り当ての確認

- ストーリー 20 本すべてが、ちょうど 1 つの主担当ユニットに割り当てられている（U1: 11 本、U2: 8 本、U3: 1 本）。
- すべてのユニットに 1 本以上のストーリーがある。
- 各ストーリーの受け入れ基準は、すべて主担当ユニットの中で満たせる（ユニットをまたぐ受け入れ基準はない）。
