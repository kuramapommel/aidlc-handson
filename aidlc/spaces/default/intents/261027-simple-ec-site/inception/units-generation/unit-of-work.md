# ユニット定義（Unit of Work）

ドメイン設計の 7 コンポーネント（`../domain-design/components.md`）を、機能の縦割りで 3 つのユニットにまとめる（`units-generation-questions.md` Q1）。各ユニットは、その機能に必要な Rust 側（業務コンポーネント・WebApi・InMemoryStore）と MoonBit 側（WebUi）の部分をまとめて持ち、ユニット単独で動作確認できる。

## ユニット一覧

| Unit ID | Directory | 名前 | 概要 | 規模 | 種別 |
| --- | --- | --- | --- | --- | --- |
| U1 | u1-purchase-skeleton | 購入の最小の流れ（ウォーキングスケルトン） | 探索なしで「コース一覧 → 日程の選択 → 購入確認 → 購入 → e チケット表示」が端から端まで動く最小の切れ端。monorepo の土台を含む | L | 指定なし（Rust と MoonBit の両方にまたがるため） |
| U2 | u2-course-search | コース探索 | キーワード・カテゴリ・空席ありのみ・期間での絞り込み、並べ替え、URL への反映、0 件・読み込み失敗の表示 | M | 指定なし（同上） |
| U3 | u3-my-tickets | 購入済みチケット | 操作中の従業員の購入済み e チケットの一覧と詳細 | S | 指定なし（同上） |

種別（`service` / `spec` / `ui` / `packaging` / `library`）は、どのユニットも Rust の実行ファイルと MoonBit の画面の両方にまたがり 1 つに当てはまらないため付けない。コンストラクションでは、各ユニットで設計書一式（機能設計・NFR 要件）を作る。

## 配置のモデル（共通）

`units-generation-questions.md` Q3 の回答により、ローカルでは 2 プロセスで動かす。

| プロセス | 中身 | 備考 |
| --- | --- | --- |
| Web API サーバー | Rust の実行ファイル 1 つ（WebApi が業務コンポーネントと InMemoryStore を組み立てて起動） | 画面のオリジンからの通信を許可する（CORS） |
| 画面用の静的ファイルサーバー | MoonBit を JavaScript にビルドした結果と HTML・CSS を配信する | 具体的な配信手段はコンストラクションで決める |

どのユニットも同じ 2 つのプロセスに機能を足していく（ユニットごとに別のプロセスを増やさない）。リポジトリは monorepo とし、Rust のワークスペースと MoonBit のプロジェクトを 1 つのリポジトリに置く（要件 C7）。

## U1. 購入の最小の流れ（u1-purchase-skeleton）

### 説明と境界

探索の機能を持たない最小の購入の流れを、画面から Web API・業務ロジック・データストアまで端から端まで実際に動かす。最初に作り、実際に動かして確認してから U2・U3 に進む（ウォーキングスケルトン。`units-generation-questions.md` Q2）。

### 担当すること

- **monorepo の土台**: Rust のワークスペース、MoonBit のプロジェクト、2 プロセスでの起動手順（README）
- **CourseCatalog**: コースと開催日程の型、全コースの一覧（探索条件なし、既定の並び）、コースの詳細、日程ごとの残席数と状態（購入可・満席・受付終了）の判定、一覧用の集計（直近の開催日・空席のある日程の数）
- **Eligibility**: 企業と従業員の型、利用資格の判定（契約中のみ購入可。存在しない従業員と契約終了企業を区別）、切り替え用の従業員一覧
- **TrainingBudget**: 予算取引の型、残高・不足額・購入後残高の計算、消費取引の生成
- **Purchasing**: チケットの型、購入の決定関数（利用資格・日程の存在・受付終了・満席・購入済み・残高不足の検証）、チケット番号の発行、チケット 1 枚の詳細、日程ごとの発行済み数
- **InMemoryStore**: 上記の読み書き関数のメモリ実装、状態更新の直列化と購入の決定の一括記録、初期データの生成
- **WebApi**: コース一覧・詳細、操作中の従業員と残高、切り替え用の従業員一覧、購入、チケット詳細の各受け口。要求の検証とログ、操作中の従業員 ID の受け取り、CORS
- **WebUi**: TEA の実行の土台、ヘッダー（従業員名・残高・切り替え）、コース一覧（探索なし）、コース詳細と日程選択、購入確認、完了と e チケット表示、購入の拒否理由の表示、契約外企業の案内

### 規模

L（monorepo の土台と、7 コンポーネントすべての最初の部分を含むため）

### 実装上の注意・制約

- 業務ロジックは純粋関数で書き、副作用（HTTP、データストア、画面描画）は境界に閉じ込める（要件 NFR6、ADR-001）。
- 購入は「決定関数」と「データストアでの一括記録」に分ける（ADR-004）。同時購入で定員を超えないことを、この時点でテストで確認する。
- 発行済み数はコースカタログに関数として渡す（ADR-005）。
- 操作中の従業員 ID の受け渡しは、ローカル検証専用の前提であることを README とコードに明記する（ADR-008）。
- U2 が探索条件を足しやすいよう、コース一覧の受け口と画面の状態は、条件を後から追加できる形にしておく。

## U2. コース探索（u2-course-search）

### 説明と境界

U1 のコース一覧に、探索の機能をすべて加える。UX の重点（探しやすさ）を担うユニット。

### 担当すること

- **CourseCatalog**: 探索条件の型と検証（キーワード・カテゴリ・空席ありのみ・期間・並べ替え）、絞り込みと並べ替えの純粋関数（同値はコース ID の昇順、今後の日程がないコースは開催日順で最後）
- **WebApi**: コース一覧の受け口に探索条件を受け付ける。不正な条件値の扱い（4xx または無視）
- **WebUi**: 探索条件の入力、全画面を読み込み直さない非同期の結果更新（最後の要求の結果だけを反映）、URL への反映と復元（不正な値は無視）、件数表示、0 件の表示と「条件をリセット」、読み込み失敗と「再試行」、期間の前後関係の即時チェック、詳細から一覧へ戻ったときの条件の保持

### 規模

M

### 実装上の注意・制約

- 絞り込みと並べ替えは Web API 側で行い、画面に同じロジックを持たない（ADR-006）。
- 受講料順・コース名順の並べ替え（US1.7）は Should Have で、時間が足りない場合は後回しにできる（`../user-stories/stories.md`）。

## U3. 購入済みチケット（u3-my-tickets）

### 説明と境界

操作中の従業員が、これまでに購入した e チケットを見返せるようにする。

### 担当すること

- **Purchasing**: 従業員ごとの購入済みチケットの一覧（開催日時の近い順）
- **WebApi**: 購入済みチケットの一覧の受け口（チケット詳細の受け口は U1 で用意済み）
- **WebUi**: 購入済みチケットの一覧画面、一覧からの詳細表示、チケットがない場合の案内、U1 の完了画面とヘッダーへの「購入済みチケット」導線の追加（AC4.2.4・AC4.2.5）

### 規模

S

### 実装上の注意・制約

- 一覧に表示する項目は、U1 の完了画面と同じ e チケットの項目（AC4.1.1）を使う。
- 従業員を切り替えたら、その従業員のチケットだけが表示されること。
