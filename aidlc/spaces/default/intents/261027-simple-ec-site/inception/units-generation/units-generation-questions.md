# ユニット生成 — 確認事項

ドメイン設計の 7 コンポーネント（業務 4 つ＋Web API・データストア・Web 画面）を、実装の単位（ユニット）にまとめます。ユニットはコンストラクションで 1 つずつ「機能設計 → NFR 要件 → コード生成」を回す単位になります。

今回の進め方（workshop）では、**最初のユニットを「端から端まで実際に動く最小の切れ端（ウォーキングスケルトン）」にし、実際に動かして確認してから残りのユニットに進む**決まりがあります。

## Q1. ユニットの分け方

コンポーネントをどの切り口でユニットにまとめますか？

A. 機能の縦割り: 利用者の機能ごとに、Rust（ドメイン・API・データストア）と MoonBit（画面）をまとめて 1 ユニットにする（例: 「コース探索」「購入」「チケット」）。各ユニットが単独で動作確認できる
B. 実行単位ごと: 「Rust の Web API（ドメイン・データストアを含む）」と「MoonBit の Web 画面」の 2 つに分ける。端から端まで動くのは両方そろってから
C. コンポーネントごと: ドメイン設計の 7 コンポーネントをそのまま 7 ユニットにする

## Q2. 最初のユニット（ウォーキングスケルトン）の範囲

最初に端から端まで動かして確認する「最小の切れ端」に、どこまで含めますか？

A. コース一覧の表示だけ（初期データ → Web API → 画面に一覧が出る）。最も小さいが、購入の仕組みは確認できない
B. 探索なしの最小の購入の流れ（コース一覧 → 日程の選択 → 購入確認 → 購入 → e チケット表示）。予算・残席・利用資格の判定と一括記録まで、実際に動くことを確認できる
X. Other (please specify)

[Answer]: B. 探索なしの最小の購入の流れ

## Q3. ローカルでの起動のしかた（配置のモデル）

ローカルで動作確認するとき、Web API と画面をどう動かしますか？

A. 1 プロセス: Rust の Web API サーバーが、MoonBit をビルドした画面の静的ファイル（HTML・JS）も配信する。起動コマンドは 1 つで、同じオリジンなので通信の設定も不要
B. 2 プロセス: Rust の Web API サーバーと、画面用の静的ファイルサーバーを別々に起動する（画面から API へはオリジンをまたぐ通信の許可設定が必要）
X. Other (please specify)

[Answer]: B. 2 プロセス
