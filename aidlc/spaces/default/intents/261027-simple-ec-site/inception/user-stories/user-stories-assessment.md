# ユーザーストーリーの要否判断

## 判断

**Decision: Execute**（ユーザーストーリーを作成する）

## 理由

- 従業員が画面を直接操作する機能が中心である（コースの探索、日程の選択、購入、e チケットの確認）。要件定義書の FR2〜FR6 が該当する。
- 「優れたユーザー体験」がご依頼の主眼で、特に「コースの探しやすさ」を重視すると回答いただいている（`requirements.md` の FR2、前提 A8）。利用者の視点で受け入れ基準を書くことで、体験の良し悪しを確認できる形にできる。
- 業務ルールが複数絡む（研修予算の残高、日程ごとの定員、受付終了、重複購入の禁止、契約企業のみ購入可）。ストーリーごとに正常系と異常系を分けて書くことで、抜け漏れを防げる。

## 検討した要素

| 要素 | 評価 |
| --- | --- |
| プロジェクト種別 | 新規開発（Greenfield） |
| 利用者が触れる範囲 | 大きい（探索・詳細・購入確認・完了・チケット一覧の各画面） |
| 複雑さのシグナル | 予算と定員の整合性、同時購入、契約状態による購入可否 |
| 利用者の種類 | 契約企業の従業員（受講者）。管理者向け画面は対象外 |

## ストーリーが特に役立つ領域

- コースの探索（キーワード、カテゴリ、空席あり、開催期間、並べ替え、URL への反映）
- 日程の選択と購入の可否（満席・受付終了・購入済み・残高不足・利用できない企業）
- 購入確定時の整合性（二重送信、最後の 1 席の同時購入）
