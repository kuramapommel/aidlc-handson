# ユーザーストーリー — 作成方針と確認事項

## ストーリー作成の方針（案）

- **形式**: 「〈ペルソナ〉として、〈したいこと〉をしたい。なぜなら〈得られる価値〉だからだ」の形で書き、INVEST（独立している、交渉可能、価値がある、見積もれる、小さい、テストできる）を満たすようにする。
- **受け入れ基準**: Given/When/Then 形式で、正常系に加えて異常系・境界値を含める。
- **優先度**: MoSCoW（Must Have / Should Have / Could Have / Won't Have）で付ける。最終的な MVP の線引きは後の工程で決める。
- **追跡**: 各ストーリーに `US{グループ}.{連番}`、各受け入れ基準に `AC{グループ}.{連番}.{連番}` の ID を付け、要件定義書の FR / NFR との対応を `traceability.json` に記録する。

以下の質問で、ペルソナ・分け方・粒度・優先度を決めます。

## Q1. ペルソナ（利用者像）の分け方

要件定義書では利用者は「契約企業の従業員（受講者）」の 1 種類です。ストーリーを書くときのペルソナをどう分けますか？受け入れ基準の観点（例: 予算が少ない人、急いでいる人）が変わります。

A. 受講者 1 種類のみ（「契約企業の従業員」としてまとめる）
B. 受講の目的や状況で 2〜3 人に分ける（例: 必修研修を期限までに受けたい人、スキルアップのために自分で探す人、予算が残り少ない人）
C. B に加えて、契約が終了した企業の従業員（購入できない人）もペルソナとして立てる
X. Other (please specify)

[Answer]: X. ペルソナは１人でいいですがより具体的なものにしたいです。たとえば「非ソフトウェアエンジニアでありながらコーディングエージェントの普及によりAI駆動開発に挑戦してみようと考えており、ファーストステップとなるような動画形式の数時間の研修を探している」などです（あくまで例なので、より現実に存在しそうなペルソナがいればそちらを採用してください）。

## Q2. ストーリーの分け方

ストーリーをどの単位でまとめますか？

A. 利用の流れ（探す → 日程を選ぶ → 購入する → チケットを確認する）に沿ってまとめる
B. 機能（探索、日程、予算、購入、チケット、アカウント）ごとにまとめる
X. Other (please specify)

※ Q1 でペルソナを 1 人に決めたため、「ペルソナごとにまとめる」の選択肢は外しました。

[Answer]: A. 利用の流れ（探す → 日程を選ぶ → 購入する → チケットを確認する）に沿ってまとめる

## Q3. ストーリーの粒度

1 つのストーリーをどのくらいの大きさにしますか？実装とテストの単位にも影響します。

A. 細かく（1 ストーリー = 1 つの振る舞い。例: 「キーワードで絞り込む」「カテゴリで絞り込む」を別々にする。全体で 15〜20 本程度）
B. 中くらい（1 ストーリー = 1 つの画面や目的。例: 「条件を組み合わせてコースを探す」。全体で 8〜10 本程度）
C. 粗く（エピック単位。全体で 4〜5 本程度）
X. Other (please specify)

[Answer]: A. 細かく（1 ストーリー = 1 つの振る舞い。全体で 15〜20 本程度）

A. 開催期間での絞り込み（要件 FR2.5）

E. すべて Must Have（後回しにしてよいものはない）
