# 技術の選定（U1 購入の最小の流れ）

U1 で使う言語・ライブラリ・リポジトリの構成を、理由とともに決める。要件定義書（`../../../inception/requirements-analysis/requirements.md`）の制約 C3（画面は MoonBit の最新版）・C4（Web API は Rust の最新 stable 版）・C5（デファクトスタンダードの最新 stable 版を積極的に使う）・C6（関数型）・C7（monorepo）と、未解決事項 OQ1・OQ2 に答える。

バージョンは 2026 年 10 月 29 日に crates.io で確かめた最新の stable 版。コード生成で依存を追加するときに、その時点の最新 stable 版を取得して `Cargo.lock` に固定する（NFR3.12）。

## 1. 言語と実行環境

| 対象 | 選定 | 理由 |
| --- | --- | --- |
| Web API | Rust 最新 stable（この環境では rustc / cargo 1.97.0）、edition 2024 | C4。所有権と不変の既定が、関数型の実装（NFR6）と相性がよい |
| 画面 | MoonBit 最新版、JavaScript 向けのビルド（`moon build --target js`） | C3。**この環境では MoonBit のツールの取得先がブロックされているため、許可されてから最新版を確かめる**（外部依存 ED-1） |
| 画面の実行環境 | 最新版の Chrome・Edge・Firefox・Safari | 要件 A9 |

## 2. Rust の crate（OQ2）

| 用途 | crate（確認した最新 stable 版） | 理由 |
| --- | --- | --- |
| Web フレームワーク | `axum` 0.8.9 | Rust で最も使われている Web フレームワークの 1 つ。ハンドラーがただの非同期関数で、状態を関数に渡す形が関数型の組み立て（NFR6.3）に合う |
| 非同期の実行環境 | `tokio` 1.54.1 | axum が前提とするデファクトの実行環境。同時購入のテスト（NFR2.2）で複数のタスクを動かすのにも使う |
| HTTP の共通部品 | `tower` 0.5.3、`tower-http` 0.7.1（CORS・要求のログ・静的ファイルの配信） | CORS の許可（NFR3.6）、要求ごとのログ（NFR10.1）、画面用の静的ファイルサーバー（Q2）を自作せずに済む |

| エラーの型 | `thiserror` 2.0.21 | 業務の結果（拒否の理由）以外の失敗を、型として明示する |
| テスト | 標準の `cargo test`、`tokio` のテスト用の実行環境、`tower` の `ServiceExt`（サーバーを起動せずに受け口を呼ぶ） | NFR8.1。Web API のテストに外部のサーバーやツールが要らない |

HTTP クライアント（`reqwest` など）は、テストでもサーバーを起動しない方針のため使わない。

## 3. 画面（MoonBit）のライブラリ（OQ1）

| 用途 | 選定 | 理由 |
| --- | --- | --- |
| TEA の実行環境・仮想 DOM・HTTP の呼び出し | MoonBit コミュニティの TEA ライブラリ `moonbit-community/rabbita`（2026-10-29 時点の最新は 0.17.0） | 確認事項 Q1 の回答（rabbit-tea）と、コード生成での判断（後継の rabbita への変更）。TEA（ADR-007）をそのまま実現でき、実行環境を自作しなくて済む |
| 画面のテスト | 標準の `moon test` | NFR8.2。更新関数を純粋関数としてテストする |

**変更の経緯（2026-10-29）**: コード生成の Step 13 で、rabbit-tea は廃止扱いで公開済みの 73 版すべてが取り下げ（yanked）られており、後継の `moonbit-community/rabbita` を使うよう案内されることが分かった。あわせて、パッケージ本体の取得先 `download.mooncakes.io` がネットワークの設定で拒否されていた。利用者の判断で、`download.mooncakes.io` を許可し、rabbita に変更した。

**rabbita が最新版で使えなかった場合**（ビルドできない、Cookie 付きの通信ができない、必要な機能がないなど）は、TEA の自作（確認事項 Q1 の B）には切り替えない。使えない原因と対策の案をまとめて報告し、判断を仰ぐ（確認事項 Q1 の回答）。

## 4. リポジトリの構成（monorepo。C7）

```text
/（リポジトリのルート）
├── Cargo.toml              Rust のワークスペース
├── crates/
│   ├── course_catalog/     業務: コースと日程（純粋関数）
│   ├── eligibility/        業務: 企業と従業員、利用資格（純粋関数）
│   ├── training_budget/    業務: 予算の取引と残高（純粋関数）
│   ├── purchasing/         業務: 購入の決定とチケット（純粋関数）
│   ├── in_memory_store/    アダプター: メモリ上のデータストアと初期データ
│   ├── web_api/            アダプター: Web API（実行ファイル。部品の組み立て）
│   └── static_server/      画面用の静的ファイルサーバー（実行ファイル。Q2）
├── web/                    MoonBit の画面のプロジェクト（rabbita）
├── scripts/verify.sh       Construction の確認コマンド（NFR9.3）
└── README.md               前提のツール、ビルド・テスト・起動の手順、ローカル検証専用の注意（NFR3.8）
```

- 業務の 4 つの crate は互いに、CourseCatalog・Eligibility・TrainingBudget を Purchasing だけが使う形にし、データストアと Web API の crate には依存しない（NFR7.1）。
- 待ち受けのポートの既定は、Web API が `3000`、画面用の静的ファイルサーバーが `8080`。環境変数で変えられる（NFR3.9）。画面のオリジンの既定は `http://localhost:8080`（NFR3.6）。

## 5. 決定と採らなかった案

### TD-1: データストアの直列化の方法（BR5.4、NFR2.2）

- **決定**: 全データを 1 つの不変な状態として持ち、排他ロックで守った「現在の状態」を置き換える。更新は「現在の状態 → 新しい状態＋結果」を返す純粋関数として書き、ロックの中で 1 件ずつ適用する。読み出しは、ロックの中で現在の状態の写しを取り出してから、ロックの外で純粋関数で計算する。
- **理由**: 可変な共有状態がこの 1 か所だけになり（NFR6.2）、ロックの中で決定をやり直すため同時購入でも定員を超えない（ADR-004）。今回の規模では、ロックの待ちは問題にならない。
- **採らなかった案**: (1) 更新専用のタスクにメッセージで依頼する方式（アクター）: 直列化は同じだが、メッセージと応答の型が増えてコードが長くなる。(2) コース・チケット・予算ごとに別々のロックを持つ方式: ロックの順番を誤るとデッドロックや不整合が起き、購入の同時反映（BR5.3）が難しくなる。
- **セキュリティ・信頼性への影響**: 1 件の要求が失敗しても、状態の置き換えは成功したときだけ行うため、状態は壊れない（NFR2.5）。

### TD-2: 画面用の静的ファイルサーバー（確認事項 Q2）

- **決定**: Rust のワークスペースに `static_server` を足し、`tower-http` の静的ファイルの配信で MoonBit のビルド結果と HTML・CSS を配る。存在しないパスには画面の入り口（`index.html`）を返し、画面内の URL（`/courses/C001` など）を直接開いても画面が動くようにする。
- **採らなかった案**: Python や Node.js の汎用の静的サーバー: 前提のツールが増える（NFR9.1）。Web API に静的ファイルの配信を持たせる 1 プロセス案: ユニット生成で 2 プロセスと決めている。

### TD-3: 画面の TEA（確認事項 Q1）

- **決定**: rabbita（rabbit-tea の後継）を使う。使えなければ原因と対策を報告して判断を仰ぐ。当初は rabbit-tea を選んだが、廃止（全版取り下げ）のため 2026-10-29 に変更した。
- **採らなかった案**: TEA の自作: 外部に依存しないが、書く量とテストが増える。確認事項 Q1 の回答で選ばないことになった。
