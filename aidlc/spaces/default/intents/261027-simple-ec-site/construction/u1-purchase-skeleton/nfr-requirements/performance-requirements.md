# 性能・操作性の要件（U1 購入の最小の流れ）

要件定義書（`../../../inception/requirements-analysis/requirements.md`）の NFR1（性能）・NFR4（ユーザビリティ）・NFR5（アクセシビリティ）を、U1 の画面と Web API に当てはめて具体化する。各要件の ID は要件定義書の NFR 番号に枝番を付けたもの。

前提: ローカル環境（開発者の PC 1 台、または開発用のクラウド環境 1 台）で、初期データの規模（企業 3 社・従業員 4 名以上・12 コース以上・日程数十件・チケット数十件）で測る。

## 性能の目標

| ID | 対象 | 目標 | 測り方 |
| --- | --- | --- | --- |
| NFR1.1 | コース一覧の受け口（`GET /api/courses`） | 95% の要求が 200 ms 以内に応答する | Web API の自動テストで、同じ要求を 100 回送って応答時間の 95 パーセンタイルを確かめる |
| NFR1.2 | コースの詳細の受け口（`GET /api/courses/{courseId}`） | 95% の要求が 200 ms 以内に応答する | NFR1.1 と同じ |
| NFR1.3 | 購入の受け口（`POST /api/purchases`）と、操作中の従業員・チケット詳細の受け口 | 95% の要求が 200 ms 以内に応答する（要件定義書の NFR1 は一覧・詳細だけを挙げているが、購入確認からの確定でも待たせないため、同じ目安を U1 の設計上の目標とする） | NFR1.1 と同じ。購入は日程を替えながら測る |
| NFR1.4 | 画面の移動（一覧 → 詳細 → 購入確認 → 完了） | 全画面を読み込み直さず、画面内の移動で表示する。Web API の応答を受けてから 300 ms 以内に表示へ反映する | ブラウザでの目視（主要な流れのデモで確かめる） |
| NFR1.5 | 処理の組み立て | 一覧の集計・日程の状態の判定は、1 回の要求の中でチケットの数を日程ごとに 1 回だけ数える（同じ数え直しを繰り返さない） | コードレビュー |

U2 で追加する「探索条件を変えてから 300 ms 以内に表示へ反映」（要件定義書 NFR1 の後半）は U2 の NFR 要件で扱う。

## 操作性の目標

| ID | 目標 | 確かめ方 |
| --- | --- | --- |
| NFR4.1 | 「コース一覧 → 日程の選択（コースの詳細）→ 購入確認 → 完了」を、ページの遷移 3 回で完了できる | デモの手順で数える |
| NFR4.2 | 読み込み中・読み込み失敗の表示を区別する（U1 の一覧は 0 件にならないが、文言を分けておく。BR7.1） | 画面の自動テスト（更新関数のテスト）と目視 |
| NFR4.3 | 確定の処理中であることが表示で分かり、確定ボタンは無効になる（BR7.3） | 画面の自動テストと目視 |
| NFR4.4 | 購入できなかったときに、理由と次の操作（別の日程を選ぶ・一覧へ戻る・もう一度試す）が必ず表示される（BR7.4、BR7.6） | 画面の自動テスト |

## アクセシビリティの目標（基本）

| ID | 目標 | 確かめ方 |
| --- | --- | --- |
| NFR5.1 | 主要な流れ（一覧 → 詳細と日程の選択 → 購入確認 → 確定 → 完了）を、キーボードだけで操作できる | 手動確認（Tab・Shift+Tab・Enter・Space・矢印キー） |
| NFR5.2 | ボタン・日程の選択の部品・従業員の切り替えの部品に、名前（ラベル）がある | 手動確認（ブラウザの開発者ツールのアクセシビリティ表示） |
| NFR5.3 | 日程の状態（受付終了・満席・購入済み）と契約外の案内は、色だけでなく文字で示し、読み上げ用のテキストにも含める（BR2.5、BR1.3） | 手動確認 |
| NFR5.4 | 選べない日程は、キーボードで移動しても選択の状態にならない（AC2.3.4） | 手動確認 |

## 前提と対象外

- 多数の利用者による負荷（同時接続数百など）は測らない。ローカル検証のため（要件 C1）。同時購入の整合性は `reliability-requirements.md` で扱う。
- 対応ブラウザは最新版の Chrome・Edge・Firefox・Safari（要件 A9）。
