# 拡張性の要件（U1 購入の最小の流れ）

要件定義書（`../../../inception/requirements-analysis/requirements.md`）の NFR7（データアクセスの差し替え）を中心に、U1 で想定する規模と、将来の拡張に備える点を定める。今回はローカル検証専用で、利用者の増加に合わせて台数を増やすような拡張は行わない（要件 C1）。

## 想定する規模

| 項目 | 想定 |
| --- | --- |
| 同時に操作する利用者 | 1〜数名（動作確認をする開発者） |
| データ量 | 企業 3 社、従業員 4〜10 名、コース 12〜20 件、日程 数十件、チケット 数十〜数百件 |
| プロセスの数 | Web API 1 つ、画面用の静的ファイルサーバー 1 つ（ユニット生成 Q3） |

## 要件

| ID | 要件 | 確かめ方 |
| --- | --- | --- |
| NFR7.1 | 業務の部品（CourseCatalog・Eligibility・TrainingBudget・Purchasing）は、データの読み書きを「関数の形」として定め、データストアの実装に直接依存しない（ADR-001）。業務の部品の crate は、データストアの crate を依存に持たない | `Cargo.toml` の依存関係とコードレビュー |
| NFR7.2 | データストアの実装を差し替えられることを、テストで示す。業務の部品のテストでは、メモリ上のデータストアではなく、テスト用の関数（固定のデータを返すクロージャ）を渡して動かす | 業務の部品の自動テスト |
| NFR7.3 | 将来 PostgreSQL に移すときに必要な保証（購入の検証と記録を 1 つのトランザクションで行い、日程の行のロックまたは「従業員と日程の組」の一意制約で重複と定員超過を防ぐ）を、データストアの関数の形のコメントに書いておく（ADR-004） | コードレビュー |
| NFR2.3 | 同時に届いた購入の要求は、データストアの更新を 1 か所で 1 件ずつ順に適用して処理する（BR5.4）。書き込みの並行性は低くなるが、想定する規模では問題にならない | 同時購入の自動テスト（`reliability-requirements.md` NFR2.2） |
| NFR7.4 | コース一覧の受け口と画面の状態は、U2 が探索条件（キーワード・カテゴリ・空席ありのみ・期間・並べ替え）を後から追加できる形にする（ユニット定義の注意） | コードレビュー（U2 の機能設計の時点で確かめる） |

## 対象外

- 複数台での運用、キャッシュ、データの分割は扱わない。
- 残高をそのつど取引の合計で計算する方式（ADR-002）は、取引が増えると遅くなる。今回の規模では問題にならないため、集計の工夫（スナップショットなど）は行わない。
