# 単体テストの手順（U1 購入の最小の流れ）

## テストの仕組みと設定

| 対象 | 仕組み | 設定 |
| --- | --- | --- |
| Rust の業務 4 crate・データストア・静的ファイルサーバー | 標準のテスト（`#[test]`）。同時購入のテストは tokio のテスト用の実行環境（`#[tokio::test(flavor = "multi_thread")]`） | 追加の設定ファイルなし。各 crate の `src/` 内の `#[cfg(test)]` モジュールと `tests/` に置く |
| Rust の Web API | 標準のテスト＋tokio。サーバーを起動せず、`tower` の `ServiceExt::oneshot` で受け口を直接呼ぶ | `crates/web_api/tests/` に置く。ポートを使わない |
| MoonBit の画面 | 標準の `moon test`（JavaScript 向け。テストの実行に Node.js を使う。2026-10-29 に前提として承認）。更新関数（メッセージ＋状態 → 新しい状態＋コマンド）を純粋関数としてテストする | `web/` のパッケージ内の `*_test.mbt` |

## このユニットのテストの実行コマンド

リポジトリのルートで実行する。U1 の crate と画面のプロジェクトだけを指定する。

```bash
# Rust（U1 で作る 7 crate だけ）
cargo test -p course_catalog -p eligibility -p training_budget -p purchasing -p in_memory_store -p web_api -p static_server

# MoonBit の画面（U1 の画面のプロジェクトだけ）
moon -C web test --target js
```

最初のテストの前（Step 2）に、Rust のコマンドが 0 件のテストで成功することを確かめる。MoonBit のコマンドは、MoonBit のツールが導入できたあと（Step 13）に確かめる。導入できない場合は MoonBit のテストは実行できないため、実行できなかったことをそのまま報告する（成功とは扱わない）。

## テストの量と目標

テストの方針は Minimal（要件ごとに 1 件、部品ごとに成功の場合を 1 件以上）。そのうえで、機能設計の境目と、NFR 要件で「自動テスト」で確かめるとしたものを含める。おおよその件数:

| 対象 | 件数の目安 | 主な中身 |
| --- | --- | --- |
| course_catalog | 6〜8 | 日程の状態の判定の順と境目、直近の開催日、既定の並び、ID の形式 |
| eligibility | 3 | 利用資格の 3 つの結果 |
| training_budget | 3〜4 | 残高、残高ちょうど、不足額 |
| purchasing | 10〜12 | 承認、7 つの拒否の理由、理由の重なり、金額を使わない、チケット番号の形式と作り直し |
| in_memory_store | 5〜6 | 同時記録、拒否で不変、同時購入（残席 1 に 2 件、定員 3 に 20 件、同じ従業員の重ね打ち）、初期データ |
| web_api | 14〜16 | 受け口の形、400・403・404・409、Cookie の属性と切り替え、CORS、金額の改ざん、応答時間 |
| static_server | 3 | 配信、`index.html` への置き換え、ディレクトリの外を配信しない |
| 画面（MoonBit） | 約 12 | `code-generation-plan.md` の Step 15 の項目 |

行カバレッジの下限は、この進め方（workshop）では設けない。既存のテスト（このユニットが最初のため、なし）はすべて成功のままにする。テストが常に成功するだけの内容（何も確かめないテスト）は書かない。

## モックとスタブの方針

- 業務の部品は純粋関数なので、モックの仕組みは使わない。必要なデータは値として渡し、データの取得・発行済み数・現在時刻・乱数は、固定の値を返すクロージャを渡す（NFR7.2、NFR8.4）。
- データストアのテストは本物のメモリのデータストアを使う。
- Web API のテストは、本物のメモリのデータストアを固定の時刻で組み立てて使う。
- 画面のテストは更新関数だけを対象にし、Web API の応答はメッセージ（成功・失敗・拒否）として直接与える。ブラウザや Web API は使わない。

## テストデータ

- 時刻は固定する（例: 2026-11-02T10:00:00+09:00）。初期データの日程は、その時刻を基準に生成される。
- テストごとに新しいデータストアを作り、テストどうしで状態を共有しない。
- チケット番号の乱数は、テストでは決まった並びを返す関数を渡す（重複時の作り直しを確かめるため、わざと同じ番号を返す関数も使う）。
