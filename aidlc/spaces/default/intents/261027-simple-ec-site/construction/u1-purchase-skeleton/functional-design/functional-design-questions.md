## Q1. 購入を拒否する理由が重なったときの優先順

購入の確定時、拒否の理由が同時に複数当てはまることがあります（例: 契約が終了した企業の従業員が、満席の日程を、残高不足のまま購入しようとした）。Web API が返し、画面に表示する理由を 1 つに決める順番をどうしますか？

A. 「利用できない企業（または存在しない従業員）→ 日程が存在しない → 受付終了 → 購入済み → 満席 → 残高不足」の順で、最初に当てはまった 1 つを返す（本人が変えられない理由を先に、予算を最後にする）
B. 当てはまる理由をすべて返し、画面では上の順で先頭の 1 つを大きく表示し、残りは小さく並べる
X. Other (please specify)

[Answer]: A. 最初に当てはまった 1 つを返す（回答者のことば: 「最後の購入トランザクション時のチェックプロセスの話をしていますか？それであれば「ひとつだけ返す」で良いです。」。画面の各所で選べないように制御したうえで、購入確定時に Web API が行う最終チェックの話であることを確認済み）

## Q2. 操作中の従業員 ID の受け渡し方法

C. Cookie に入れる
X. Other (please specify)

[Answer]: C. Cookie に入れる（HTTP ヘッダー・Cookie それぞれの理由を説明したうえでの選択。将来の本番の形に近い。切り替え時に Web API が Cookie を発行し、CORS の資格情報の設定と購入の CSRF 対策を入れる）

## Q4. コース一覧に出す「直近の開催日」の数え方

## Consolidated Summary Confirmation

- 購入の拒否理由: 購入確定時に Web API が行う最終チェックで、「利用できない企業（または存在しない従業員）→ 日程が存在しない → 受付終了 → 購入済み → 満席 → 残高不足」の順に調べ、最初に当てはまった 1 つだけを返す。画面では各場面で選べない・確定できないよう事前に制御する（Q1）
- 操作中の従業員 ID: Cookie でやりとりする。切り替え時に Web API が Cookie を発行し、画面からの要求には資格情報付きで送る。Web API は画面のオリジンだけを資格情報付きで許可し、購入などの書き込みには CSRF 対策を入れる（Q2）
- 最初の従業員と再読み込み: 最初は初期データの先頭の従業員（高橋 遥）。切り替えた従業員は Cookie として保存され、再読み込みしても保たれる（Q3）
- 直近の開催日: 今後の日程（満席も含む）のうち最も早い日。空席の有無は「空席のある日程の数」で別に示し、U1 の一覧はこの日の早い順に並べる（Q4）
