# NFR 要件（U2 コース探索）— 確認事項

U2（`u2-course-search`）の性能・セキュリティ・拡張性・信頼性・可観測性の目標と、技術の選定を決めます。数値の目標（Web API の応答 200 ms 以内、条件の変更から 300 ms 以内の反映など）は要件定義書の NFR1〜NFR10 で、技術の方針は U1 の NFR 要件（rabbita・mizchi/js_web・axum など）と U2 の機能設計の確認事項（Q1〜Q5、Q2-1）で決まっています。そのため、この工程で新しく質問することはありません。下のまとめをご確認ください。

---

## Consolidated Summary Confirmation

- 性能: 探索条件付きのコース一覧の Web API は、条件の組み合わせを替えても 95% の要求が 200 ms 以内に応答する。画面は、キーワードは入力が止まってから（150 ms の待ちを含めて）、ほかの条件は変えてから 300 ms 以内に表示へ反映し、全画面を読み込み直さない
- 操作性とアクセシビリティ: 読み込み中・0 件・読み込み失敗を別の表示にし、0 件では「条件をリセット」、失敗では「再試行」を必ず出す。すべての探索の入力にラベルを付け、キーボードで操作でき、件数の変化や案内を読み上げ可能な文字で伝える
- セキュリティ: 形の決まった条件は Web API がすべて検証し、不正なら 400 と不正な条件の項目名・理由だけを返す。キーワードは拒否せず先頭 200 文字で探し、文字列の一致だけで照合する。画面は受け取った文字列も入力した文字列も文字として表示する。URL の値は項目ごとに検証してから使う
- 拡張性: 絞り込みと並べ替えは CourseCatalog の純粋関数とし、将来 PostgreSQL の検索に差し替えられる形にする。テストはデータストアを使わずに動かす
- 信頼性と品質: 探索はデータを変えない。順不同で届いた応答でも最後の条件の結果を表示する。並べ替えは最後にコース ID で比べて毎回同じ順にする。キーワードの待ちは更新関数が返すコマンドで表し、更新関数の中で時計を使わない。前提のツールは増やさない
- 可観測性: 探索の要求も 1 行のログを出すが、キーワードなどの値はログに残さない（400 は項目名だけ）
- 技術の選定: キーワードの正規化に Rust の `unicode-normalization`（最新 stable 0.1.26）を足し、カタカナからひらがなへの変換は小さな純粋関数で行う。待ちは rabbita の `@cmd.delay` を使う。正規化は Web API 側だけで行い、よみがなは初期データとして持つ
