# 技術の選定（U2 コース探索）

U2 で使う技術を決める。U1 の選定（`../../u1-purchase-skeleton/nfr-requirements/tech-stack-decisions.md`。Rust の axum・tokio・serde など、画面の rabbita と mizchi/js_web、リポジトリの構成）はそのまま引き継ぎ、ここでは U2 で足すもの・決めることだけを書く。要件定義書（`../../../inception/requirements-analysis/requirements.md`）の制約 C5（デファクトスタンダードの最新 stable 版を使う）に従う。

## 1. 足すもの

| 用途 | 選定 | 理由 |
| --- | --- | --- |
| キーワードの正規化（全角半角・互換文字の統一） | Rust の `unicode-normalization`（2026-10-29 時点の最新 stable は 0.1.26） | Unicode の正規化（NFKC）で、全角英数字の半角化・半角カタカナの全角化をまとめて行える。Rust で Unicode の正規化を行うデファクト（累計の取得数が非常に多い）。CourseCatalog の crate に足す |
| カタカナからひらがなへの変換・英字の小文字化 | 追加の crate なし（標準ライブラリの文字の変換と、カタカナとひらがなの符号の差で変換する小さな純粋関数） | 変換の規則が単純（カタカナの範囲をひらがなの範囲へずらす）で、ライブラリを足すほどではない。テストで変換の表を確かめる |
| キーワードの入力の待ち（150 ms） | rabbita の `@cmd.delay`（U1 で使っている rabbita 0.17.0 に含まれる） | TEA のコマンドとして待ちを表せ、更新関数を純粋に保てる（NFR6.2）。新しい依存は増えない |
| URL のクエリの読み書き | rabbita の URL の扱い（U1 で使用済み）と、標準の URL のエンコード | U1 と同じ仕組みで、新しい依存は増えない |

## 2. 決めたこと

### TD-U2-1: 照合のための正規化を Web API 側だけで行う

- **決定**: キーワード・コース名・概要の正規化は、Web API（CourseCatalog）だけで行う。画面は利用者が打った文字列をそのまま送る。
- **理由**: 探索のロジックを 1 か所に置く決定（ADR-006）に合わせる。画面と Web API で正規化が食い違う心配がない。
- **採らなかった案**: 画面でも正規化してから送る: 2 言語に同じ規則が重複する。

### TD-U2-2: よみがなは初期データとして持つ

- **決定**: コースのよみがな（titleReading）は初期データに書き、実行時に漢字から読みを推定しない。
- **理由**: 漢字の読みの推定には辞書が必要で、今回の規模（十数コース）では手で書くほうが正確で単純。
- **採らなかった案**: 形態素解析のライブラリで読みを推定する: 依存と辞書が大きく、誤読もある。

### TD-U2-3: キーワードの比較は正規化した文字列の部分一致

- **決定**: 正規化したコース名・概要に、正規化した各検索語が部分文字列として含まれるかで判断する。
- **理由**: 要件（FR2.2）の「含むもの」に合い、初期データの規模では十分に速い。
- **採らなかった案**: 全文検索の索引を作る: 今回の規模では効果が小さい。
