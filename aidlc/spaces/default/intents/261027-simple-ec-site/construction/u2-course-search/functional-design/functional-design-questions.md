## Q2. Web API が不正な探索条件を受け取ったとき

URL に存在しないカテゴリや不正な日付があっても、画面はエラーにせず、不正な条件だけを無視して一覧を表示します（AC1.8.3）。一方、Web API に不正な条件（存在しないカテゴリ、日付の形式違い、終了日が開始日より前など）が直接届いた場合は、ドメイン設計で「4xx か無視」と決め切っていませんでした。どちらにしますか？

A. 400 で拒否し、どの条件が不正かを返す。画面は不正な条件を Web API に送らない（URL から読むときに捨てる）ので、通常の操作では起きない
B. 不正な条件だけを無視して、残りの条件で結果を返す（画面と同じ扱い）

[Answer]: X. 基本は 400 で拒否する。ただし入力中の中途半端な状態で送られて 400 が返ると不便なので、その対策を考える（回答者のことば: 「基本400で良いですが、入力中の中途半端な状態で送信されて400返されると不便なのでそこについては対策を考えたいです。おすすめの実装を教えてください。」）。対策は Q2-1 で決める

## Q3. 期間で絞り込んでいるときの「直近の開催日」と並び

B. 期間に関係なく、今後の日程（満席も含む）のうち最も早い日を表示し、その日で並べる（U1 と同じ。期間は絞り込みだけに使う）

## Q4. 「コース名順」の並べ方

[Answer]: A. コースに「よみがな」を持たせ、よみがなの五十音順に並べる（同じよみがなはコース ID の昇順）

## Q2-1. 入力中の中途半端な条件で 400 が返らないようにする対策（Q2 の追加確認）

Q2 で「Web API は不正な条件を 400 で拒否する。ただし入力中の中途半端な状態で 400 が返ると不便」となりました。対策をどうしますか？

A. 画面が送る前に、Web API と同じ規則で条件を確かめ、正しくそろった条件だけを送る（おすすめ）。具体的には、日付の欄はブラウザの日付の入力欄を使い、空か正しい日付しか値にならないようにする。終了日が開始日より前のときは送らず、入力欄の近くに「期間の指定が正しくありません」と出して、一覧はそれまでの結果のままにする（AC1.5.3）。キーワードは、どんな文字でも正しい条件として扱い、長さの上限（100 文字）は入力欄でそれ以上打てないようにする。カテゴリと並べ替えは選択肢から選ぶだけにする。こうすると通常の操作では 400 は起きず、400 は URL の手入力や直接の呼び出しのときだけになる。万一 400 が返ったときは、一覧を前の結果のままにして「条件を確かめてください」と出す
B. Web API に「条件の確認だけ」の受け口を足し、入力のたびに確かめる（画面と Web API で確かめ方を二重に持たずに済むが、通信が増える）

### Q2-1 の見直し（ご質問を受けて）

ご質問: 「それは逆に自由入力の制限にならないですか？自由入力系の検索におけるベストプラクティスですか？」

ご指摘のとおり、自由入力のキーワードに上限を設けて打てなくするのは、自由入力の検索の一般的なやり方ではありません。自由入力の検索では、どんな文字列も「正しい検索語」として受け取り、拒否しないのが一般的です。打っている途中の文字列も、それ自体が検索語になります。確かめる対象は、選択肢や日付のように形が決まっている条件だけにします。この考えで次のように直します。

A. キーワードは確かめない（どんな文字列でも受け付け、Web API も 400 にしない）。極端に長い入力は、Web API が先頭の 200 文字だけを使って探し、拒否はしない。画面の入力欄にも上限を設けない。形の決まった条件（カテゴリ・並べ替えは選択肢から選ぶ、日付はブラウザの日付の入力欄で空か正しい日付だけになる）は、画面が送る前に Web API と同じ規則で確かめる。終了日が開始日より前のときは送らず、入力欄の近くに案内を出して一覧はそれまでの結果のままにする（AC1.5.3）。Web API の 400 は、形の決まった条件が不正なとき（URL の手入力や直接の呼び出し）だけになる
B. キーワードにも上限を設け、上限を超えたら Web API が 400 を返す（画面は入力欄の近くに「長すぎます」と案内する）
X. Other (please specify)

[Answer]: A. キーワードは確かめない（どんな文字列でも受け付け、上限も設けない。長すぎる入力は Web API が先頭 200 文字で探す。形の決まった条件だけ画面で確かめてから送る）
