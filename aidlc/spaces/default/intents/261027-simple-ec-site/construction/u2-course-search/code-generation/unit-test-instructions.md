# 単体テストの手順（U2 コース探索）

## テストの仕組みと設定

| 対象 | 仕組み | 置き場所 |
| --- | --- | --- |
| 探索の業務ロジック（Rust） | 標準のテスト（`#[test]`） | `crates/course_catalog/src/search_tests.rs`（`search_tests` モジュール） |
| 初期データのよみがな（Rust） | 標準のテスト | `crates/in_memory_store/src/tests.rs` の `reading_` で始まるテスト |
| Web API の探索の受け口（Rust） | 標準のテスト＋tokio。サーバーを起動せず `tower` の `ServiceExt::oneshot` で呼ぶ（U1 と同じ） | `crates/web_api/tests/search.rs` |
| 画面の探索（MoonBit） | 標準の `moon test`（JavaScript 向け。Node.js を使う） | `web/search_test.mbt` |

## このユニットのテストの実行コマンド

リポジトリのルートで実行する。U2 のテストだけを指定する。

```bash
# Rust（U2 の探索のテストだけ）
cargo test -p course_catalog search_tests
cargo test -p in_memory_store reading_
cargo test -p web_api --test search

# MoonBit（U2 の画面の探索のテストだけ）
moon -C web test --target js --file search_test.mbt
```

Step 2 で、各コマンドが 0 件のテストで成功することを確かめる。MoonBit のファイル指定のオプションが今の moon で使えない場合は、同じ意味の指定に置き換え、置き換えたコマンドを `code-summary.md` に書く。

U1 のテストが壊れていないことは、Construction の確認コマンド（`bash scripts/verify.sh`）で全体を実行して確かめる。

## テストの量と目標

| 対象 | 件数の目安 | 主な中身 |
| --- | --- | --- |
| 探索の業務ロジック | 15〜18 | 正規化（全角・小文字・かな・全角スペース・200 文字・空白だけ）、検証の不正値、絞り込み（AC1.2〜AC1.5）、並べ替え（AC1.6〜AC1.7、同値、予定なし、期間外の直近の開催日） |
| よみがな | 1〜2 | すべてのコースに正しい形のよみがながある |
| Web API | 6〜8 | 条件付きの応答と件数、400 と項目名、キーワードでは 400 にならない、条件なしは U1 と同じ、性能（95 パーセンタイル 200 ms）、データが変わらない |
| 画面 | 約 15 | `code-generation-plan.md` の Step 10 の項目 |

行カバレッジの下限は設けない（workshop）。U1 のテストはすべて成功のままにする。何も確かめないテストは書かない。

## モックとスタブの方針

- 探索の業務ロジックは純粋関数なので、モックの仕組みは使わない。コース・日程は値として渡し、発行済み数と現在時刻は固定の値を返すクロージャで渡す（NFR7.2）。
- Web API のテストは、本物のメモリのデータストアを固定の時刻で組み立てて使う（U1 と同じ）。
- 画面のテストは更新関数だけを対象にし、Web API の応答（成功・0 件・失敗・400）と待ち終わりはメッセージとして直接与える。ブラウザ・Web API・実際の時間待ちは使わない。

## テストデータ

- 時刻は固定する（U1 と同じ 2026-11-02T10:00:00+09:00 など）。初期データの日程はその時刻を基準に生成される。
- 絞り込みと並べ替えのテストは、境目（同じ受講料、同じ直近の開催日、受付終了の日程にだけ空席、満席だけ）を持つ小さなテスト用のデータを使う。
- テストどうしで状態を共有しない。
