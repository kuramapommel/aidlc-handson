# NFR 要件（U3 購入済みチケット）— 確認事項

U3（`u3-my-tickets`）の性能・セキュリティ・拡張性・信頼性・可観測性の目標と、技術の選定を決めます。数値の目標（Web API の応答 200 ms 以内など）は要件定義書の NFR1〜NFR10 で、技術の方針は U1・U2 の NFR 要件で、振る舞いは U3 の機能設計（BR12〜BR14）で決まっています。U3 は読み出しだけの小さな機能で、新しい技術も使わないため、この工程で新しく質問することはありません。下のまとめをご確認ください。

---

## Consolidated Summary Confirmation

- 性能: 購入済みチケットの一覧の Web API（`GET /api/tickets`）は、初期データの規模で 95% の要求が 200 ms 以内に応答する。一覧のチケットを開くときは通信せず、操作した直後の再描画で詳細を表示する
- 操作性とアクセシビリティ: 読み込み中・0 件・読み込み失敗を別の表示にし、0 件では「コース一覧へ」、失敗では「再試行」を必ず出す。ヘッダーと完了画面から 1 回の操作で一覧へ移れる。開閉のボタンはキーボードで操作でき、名前と開閉の状態を支援技術に伝える。「受講済み」は色だけでなく文字で示す
- セキュリティ: 一覧は Cookie の操作中の従業員のチケットだけを返し、URL や本文で従業員を指定させない。存在しない従業員は空の一覧にする。応答とログに他人のチケットを含めない。画面はコース名などを文字として表示する。読み出しの要求なので CSRF 対策の対象外（U1 と同じ扱い）
- 拡張性: 一覧の絞り込み・受講済みの判定・並べは Purchasing の純粋関数とし、将来 PostgreSQL の「従業員 ID で引く検索」に差し替えられる形にする。テストはデータストアを使わずに動かす
- 信頼性と品質: 一覧はデータを書き換えない。現在時刻は関数の引数で受け取り、受講済みの境目（開始日時ちょうど）や同じ開催日時の並びを固定の時刻でテストする。従業員の切り替えで前の一覧と開閉の状態を捨てることを画面のテストで確かめる。前提のツールは増やさず、確認コマンド（`bash scripts/verify.sh`）で U3 のテストも動く
- 可観測性: 一覧の要求も U1 と同じ 1 行のログ（メソッド・パス・状態コード・処理時間）を出し、チケット番号や従業員名などの内容はログに出さない
- 技術の選定: 新しいライブラリは足さない（U1・U2 の axum・serde・rabbita・mizchi/js_web をそのまま使う）
