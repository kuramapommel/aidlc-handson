# 技術の選定（U3 購入済みチケット）

U3 で使う技術を決める。U1 の選定（`../../u1-purchase-skeleton/nfr-requirements/tech-stack-decisions.md`。Rust の axum・tokio・serde など、画面の rabbita と mizchi/js_web、リポジトリの構成）と U2 の選定はそのまま引き継ぐ。要件定義書（`../../../inception/requirements-analysis/requirements.md`）の制約 C5（デファクトスタンダードの最新 stable 版を使う）に従う。この工程の決定のまとめは `nfr-requirements-questions.md` で確認済み（2026-11-03）。

## 1. 足すもの

なし。U3 は既存の依存だけで作れる。

| 用途 | 使うもの | 理由 |
| --- | --- | --- |
| 一覧の受け口 | U1 の axum のルーターに `GET /api/tickets` を足す | 既存の受け口と同じ組み立て方（関数の部分適用）で足せる |
| 応答の JSON | U1 の serde | チケット詳細の応答と同じ項目の形を使える |
| 画面の通信・URL | U1 の mizchi/js_web（Cookie 付きの fetch）と rabbita（Route・コマンド） | 既存の部品で足りる |
| 日時とポイントの表示 | U1 の表示の関数（日本時間・3 桁区切り） | 完了画面と同じ表示になる |

## 2. 決めたこと

### TD-U3-1: 一覧の応答に詳細の項目まで含める

- **決定**: `GET /api/tickets` は、各チケットに AC4.1.1 の 7 項目と受講済みかどうかを含めて返す。画面はチケットを開くときに通信しない（BR13.2）。
- **理由**: 一覧の中で開く見せ方（確認事項 Q2）で、開くたびの待ちと失敗の表示をなくせる。1 人のチケットは少数で、応答が大きくなる心配がない。
- **採らなかった案**: 開くときに U1 のチケット詳細の受け口を呼ぶ: 開くたびに読み込み中と失敗の表示が要り、画面の状態が増える。

### TD-U3-2: 受講済みの判定は Web API の時計で行う

- **決定**: 受講済みかどうかは Web API が一覧を作るときに決め、画面は応答の値を表示するだけにする（BR12.3）。
- **理由**: 「開催日時を過ぎたか」の判定は Web API の時計で行うという前提（要件 A6）と、日程の受付終了の判定にそろえる。画面の時計のずれの影響を受けない。
- **採らなかった案**: 画面の時計で判定する: 利用者の端末の時計に左右され、Web API の受付終了の判定と食い違うことがある。
