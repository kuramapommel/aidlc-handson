# 単体テストの手順（U3 購入済みチケット）

## テストの仕組みと設定

| 対象 | 仕組み | 置き場所 |
| --- | --- | --- |
| 一覧の業務ロジック（Rust） | 標準のテスト（`#[test]`） | `crates/purchasing/src/owned_tickets_tests.rs`（`owned_tickets_tests` モジュール） |
| Web API の一覧の受け口（Rust） | 標準のテスト＋tokio。サーバーを起動せず `tower` の `ServiceExt::oneshot` で呼ぶ（U1・U2 と同じ） | `crates/web_api/tests/my_tickets.rs` |
| 画面の一覧（MoonBit） | 標準の `moon test`（JavaScript 向け。Node.js を使う） | `web/my_tickets_test.mbt` |

新しいテストの仕組みや設定ファイルは足さない（U1・U2 の設定をそのまま使う）。

## このユニットのテストの実行コマンド

リポジトリのルートで実行する。U3 のテストだけを指定する。

```bash
# Rust（U3 の一覧のテストだけ）
cargo test -p purchasing owned_tickets_tests
cargo test -p web_api --test my_tickets

# MoonBit（U3 の画面のテストだけ）
moon -C web test --target js --file my_tickets_test.mbt
```

Step 2 で、各コマンドが 0 件のテストで成功することを確かめる。MoonBit のファイル指定のオプションが今の moon で使えない場合は、U2 と同じく同じ意味の指定に置き換え、置き換えたコマンドを `code-summary.md` に書く。

U1・U2 のテストが壊れていないことは、Construction の確認コマンド（`bash scripts/verify.sh`）で全体を実行して確かめる。

## テストの量と目標

| 対象 | 件数の目安 | 主な中身 |
| --- | --- | --- |
| 一覧の業務ロジック | 6〜8 | 近い順の並び（AC4.2.1）、他人のチケットを含めない、存在しない従業員は 0 件、受講済みは後ろに新しい順、開始日時ちょうどは受講済み、同点の並び、データの不整合 |
| Web API | 5〜7 | 一覧と並び、他人のチケットを含めない（クエリの従業員 ID は無視）、空の並び（チケットなし・存在しない従業員）、購入の直後に含まれる、データが変わらない、性能（95 パーセンタイル 200 ms） |
| 画面 | 約 10 | `code-generation-plan.md` の Step 8 の項目 |

行カバレッジの下限は設けない（workshop）。U1・U2 のテストはすべて成功のままにする。何も確かめないテストは書かない。各部品は成功の場合に加えて 2 つ以上の失敗・境目の場合を持つ。

## モックとスタブの方針

- 一覧の業務ロジックは純粋関数なので、モックの仕組みは使わない。チケットは値として渡し、日程とコース・従業員は固定の値を返すクロージャで、現在時刻は固定の値で渡す（NFR7.3）。
- Web API のテストは、本物のメモリのデータストアを固定の時刻で組み立てて使う（U1・U2 と同じ）。
- 画面のテストは更新関数と描画の関数だけを対象にし、Web API の応答（成功・0 件・失敗）はメッセージとして直接与える。ブラウザ・Web API は使わない。

## テストデータ

- 時刻は固定する（U1・U2 と同じ 2026-11-02T10:00:00+09:00 など）。初期データの日程はその時刻を基準に生成される。初期データでは E005・E006 がそれぞれ 3 枚のチケットを持つ。
- 受講済みと並びのテストは、開始日時が現在時刻より前・ちょうど・後のチケットと、同じ開始日時・同じ購入日時のチケットを持つ小さなテスト用のデータを使う。
- テストどうしで状態を共有しない。
